## Open, in the order I would do them

### 1. Deploy what is built
Web redeploy (`deploy-platform.yml --ref one-order-screen -f
image_tag=v2026.11.28.1`), kitchen tablet build, and the customer app build
(Android and iOS). The owner held the customer app build because more
customer changes were coming; ask before building it.

### 2. Account by phone, for real (the owner wants guests gone)
Decided: everyone makes an account, by phone number, verified, at the moment
they send their first order; for a delivery the address sheet's own name and
number are the account, so only the code is new. Not decided: how the code is
proved.
- The owner prefers **WhatsApp, the customer sends** (free). It needs a Meta
  business verification and a number, which only he can do. I owe him a
  click-by-click list for that set-up.
- No set-up alternative: **Firebase phone sign-in** (about $0.16 an SMS to
  Egypt when looked up; check the live price).
- To build: a phone credential in Keycloak (as `src/keycloak-pin` does for
  the PIN; the owner's rule is best practice and nothing invented for
  sign-in), the sender behind an interface with a test mode, the web gate
  wired to it (replace `PREVIEW_CODE` in `phone-gate.tsx`), the same gate in
  the customer app, then ordering requires an account, then the guest code
  is removed (about 40 web files and 148 server files mention guests).
- Ask: does paying a bill or opening a receipt from a link need an account?
  I recommended leaving those open.

### 3. Tablet till: receipts page
Port the web's receipts redesign and the tick-to-refund lines to
`pos_app/lib/features/receipts` (`receipts_screen.dart`,
`receipt_pane.dart`). Not started.

### 4. Till mock-ups waiting for his word
In `Desktop/ninja-till-receipts-availability-mockup.html`:
- **Availability**: categories down the side (my pick) or one scrolling row.
- **Move to a named bill**: the bill's people as one-tap names, a new name
  typed in the search box. He asked about it twice and has not said yes.
He called my hand-drawn customer mock-ups bad; for the till, consider
building these from the real `pos_web` components the way `.mock` does.

### 5. Cancel one item of a sent order
He asked for a cancelled line on the kitchen ticket. It is not a backend
flag: today the till can void a whole bill or refund lines after settling,
and nothing in between. It needs "cancel an item" at the till (reason, what
becomes of the food), the bill, stock and points adjusted, and the line
struck on both kitchen displays. Waiting for his yes; start with a mock-up
of the till side.

### 6. Dock, what is left
- An order on its way goes out of sight when the tray holds an unsent one.
  He disliked the pill over the dock; the quiet option is the stage inside
  the tray's own row.
- The headline's minutes are the preview's figures. The server has minutes
  for a delivery (`GET {id}/delivery/live`); the row does not read them yet.
- Not built: "Call waiter" as the end button at a table with nothing
  ordered; a second line with the rider and a call button during a delivery.
- He rejected: any progress mark on the dock (line, ring, pulse), an
  announcement over the dock, a taller dock, offering "your usual".

- The first-visit cue code is switched off, not removed, in both apps.

- `kds_web` has no tests.
